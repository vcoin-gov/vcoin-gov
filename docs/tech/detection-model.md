## 本页要回答的问题

1. 检测的**目标**到底是什么？是找出所有可疑地址，还是在有限人力下给出最优的复核队列？
2. 规则、图算法、机器学习三者怎么分工？各自该放在流程的哪个位置？
3. 评分怎么设计才**可解释**？每个分数能不能回溯到具体依据？
4. 怎么衡量"准不准"？没有标注数据时怎么评估？
5. MVP 做到什么程度算跑通？分几步走？

::: tip 先把目标定对
**目标不是"识别所有可疑地址"，而是"在每天能复核 N 个的上限内，最大化命中率"。** 一个召回率 95% 但每天产出 5000 条告警的系统，实际可用性为零——没人看得完。这是本页所有设计的前提。
:::

## 一、三层架构

不要把它当成"选一个方法"，三层是叠加关系，各司其职。

| 层 | 作用 | 方法 | 输出 | 为什么放在这一层 |
| --- | --- | --- | --- | --- |
| **L0 过滤层** | 排除已知正常主体 | 白名单、已知交易所/项目方地址 | 丢弃 | 处理掉大部分误报，成本最低 |
| **L1 规则层** | 命中单点强特征 | 阈值规则（见链上组特征清单） | 线索 | 可解释性最好，先跑出基线 |
| **L2 图算法层** | 补充结构性信息 | 最短路径、社区发现、中心度、聚类 | 结构标签 | 单点看不出的团伙关系，只能靠图 |
| **L3 模型层** | 排序与加权 | 逻辑回归 / GBDT（有标注后再上） | 优先级分数 | **只负责排序，不负责定性** |

::: warning 关于 L3 的边界
模型输出的应该是"这条线索排在队列第几位"，不是"这个地址是犯罪地址"。定性必须留给人。把定性权交给模型，既不可解释，也无法在实务中承担责任。
:::

## 二、数据流

```
链上数据源（Tronscan / Etherscan 系 API）
        │
        ▼
   原始数据缓存（PostgreSQL）
        │   交易、地址、标签快照
        ▼
   特征计算（定时任务）
        │   每个地址一组特征值
        ▼
   图谱构建（NetworkX / 内存图）
        │   地址-交易 有向图
        ▼
   评分与排序
        │   分数 + 依据列表
        ▼
   复核队列（按分数排序，每日 Top N）
        │
        ▼
   人工复核 ──▶ 标注结果回流 ──▶ 校准阈值 / 训练模型
```

**关键设计**：人工复核的结果必须**结构化回流**。没有这个闭环，系统永远停留在拍脑袋定阈值。

## 三、评分设计

### 基本形式

```
score = Σ (w_i × f_i)
```

`f_i` 是第 i 个特征的命中值（0/1 或归一化强度），`w_i` 是权重。简单加权就够，不要一上来上复杂模型。

### 权重分配（初始假设，待校准）

| 特征类别 | 权重 | 理由 |
| --- | --- | --- |
| 与已确认涉案地址的图距离 | 最高 | 结构性强，难伪装 |
| 标签交互（可靠来源） | 高 | 依赖标签质量，需双源验证 |
| 结构性特征（扇入扇出、周期性归集） | 高 | 人工操作留下的形状，难伪装 |
| 时序特征（快转、拆分） | 中 | 可被刻意规避 |
| 金额形态（整数、重复） | 低 | 误报太多 |

### 必须输出"依据"，不只是分数

每条告警要带可读的解释：

```
地址 Txxxx…abcd  评分 82
├─ 与 3 个已标注涉诈地址在 2 跳内可达（+30）
├─ 24h 内接收 47 笔小额入账，随即归集至 1 个地址（+25）
├─ 地址创建于 6 天前，首笔交易由他人代付 gas（+17）
└─ 归集地址周期性向 CEX 充值地址转账（+10）
```

**没有这层解释，复核人员不会信任系统，最终系统会被弃用。**

## 四、怎么评估（最容易糊弄过去的一节）

### 有标注数据时

| 指标 | 定义 | 目标（待定） |
| --- | --- | --- |
| 精确率 | 判为可疑中真正可疑的比例 | 优先保证 |
| 召回率 | 真正可疑中被发现的比例 | 次优先 |
| 每日告警量 | 每天产出的待复核条目 | **必须可控** |
| 复核耗时 | 单条平均复核时间 | 越短越好 |

### 没有标注数据时（第一阶段必然如此）

三个替代办法，都要做：

1. **回溯验证**：拿[公开通报案例库](../policy/cases)里的已知涉案地址做测试集，看能不能命中。样本少但真实。
2. **抽样人工核**：每天从高分队列里抽 20 条人工判断，记录误报原因。这是前期最有效的评估方式。
3. **稳定性测试**：同一个地址在不同时间窗口跑，结果应基本一致。波动大说明阈值不稳。

::: danger 常见的自欺欺人
- 拿训练集当测试集，AUC 0.98，实际一用就废
- 用合成数据评估，分布是造的，指标无意义
- 只报召回率不报告警量，看起来很美，实际没法用
:::

## 五、MVP 分阶段

**第一阶段只做一个场景，别贪多。** 建议选「资金归集结构识别」——因为它特征明确、可验证、且直接对应治理痛点里的结构性弱点。

| 阶段 | 目标 | 输入 | 输出 | 完成标志 |
| --- | --- | --- | --- | --- |
| **M0** | 数据通路 | 一个地址 | 该地址 3 跳内的交易列表 | 能稳定拉到数据并落库 |
| **M1** | 规则筛查 | 地址列表 | 命中特征的地址 + 依据 | 在已知案例上能召回 ≥ 50% |
| **M2** | 图谱分析 | 同上 | 资金树 + 归集点识别 | 能自动画出五层结构中的 L3 |
| **M3** | 排序队列 | 全量候选 | 按分数排序的复核队列 | 每日 Top 50 里人工判真 ≥ 10 条 |
| **M4** | 闭环校准 | 复核结果 | 调整后的阈值 | 误报率比 M3 下降 ≥ 30% |

::: tip 每个阶段都可独立交付
M1 跑通就已经有价值了——它能替代手工筛地址。不要等 M4 才开始用。
:::

## 六、已知的坑

| 坑 | 表现 | 应对 |
| --- | --- | --- |
| 阈值拍脑袋 | 换个数据集就全崩 | 每条阈值标注来源，定期用真实数据校准 |
| 白名单不全 | 交易所热钱包被打成可疑 | 白名单要持续维护，宁可漏排不可错排 |
| 图规模爆炸 | 3 跳就几万节点，跑不动 | 按金额裁剪 + 聚类聚合 |
| 标签污染 | 一个错标签导致大面积误报 | 标签双源验证，标注时间超过 1 年降权 |
| 只测准确率不测可用性 | 指标好看但没人用 | 每天算"复核队列长度"这个运营指标 |
