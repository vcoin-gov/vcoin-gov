## 本页要回答的问题

1. 从**数据采集**到**可视化**，每个环节有哪些成熟开源项目？各自成熟度如何？
2. 哪些项目**已经停止维护**，不能再作为技术选型基础？
3. 哪些能力**可以自己写几百行解决**，不值得引入重型框架？
4. 最终推荐哪套组合？为什么是这套而不是别的？
5. 哪些方向**明确不做**？（避免摊子越铺越大）

::: warning 调研纪律
本页只收**能落地**的项目。判断标准三条：近一年有提交、有可运行的部署文档、许可允许内部使用。满足不了的直接排除，不要因为"GitHub star 多"就列进来。
:::

## 一、按环节拆解

链上分析的技术栈是一条流水线，每个环节独立选型，不要一上来就找"一站式平台"。

| 环节 | 要解决的事 | 候选池 | 成熟度 |
| --- | --- | --- | --- |
| **数据采集** | 从链上/API 拿原始数据 | ethereum-etl、bitcoin-etl、Blockscout、Tronscan API、Bitquery | 高 |
| **数据存储** | 存交易、地址、标签，支持图查询 | PostgreSQL、Neo4j、ClickHouse | 高 |
| **图计算** | 路径查找、社区发现、中心度 | NetworkX、igraph、Neo4j GDS | 高 |
| **地址聚类与标签** | 归集地址、打标签 | 自研为主，OFAC 名单同步 | 中（无成熟开源方案） |
| **分析平台** | 把上面几层拼起来 | GraphSense、Blockscout | 中 |
| **可视化** | 资金树、流转图 | Cytoscape.js、AntV G6、Graphviz | 高 |
| **模型** | 可疑地址分类 | GNN 类论文实现、XGBoost baseline | 低（数据依赖重） |

## 二、重点候选评估

### 数据采集层

| 项目 | 语言 | 许可 | 优点 | 问题 |
| --- | --- | --- | --- | --- |
| **ethereum-etl** | Python | MIT | EVM 链数据抽取事实标准，输出结构化 CSV/Parquet | 只能抽自己跑节点的数据，全量同步成本高 |
| **bitcoin-etl** | Python | MIT | UTXO 链数据抽取 | 维护活跃度低于 ethereum-etl |
| **Blockscout** | Elixir | GPL | 开源自托管浏览器，数据完全自主 | 部署重，需要自己的节点 |
| **Tronscan API** | — | 公开接口 | TRON 数据直接拿，无需自建 | 限流，无 SLA，字段不完整 |

::: tip 数据侧的务实结论
**第一阶段不要自建节点。** 先用公开 API + 免费额度把原型跑起来，验证思路可行后再考虑自建。自建节点是"验证完需要规模化"时才做的投入，不是起点。
:::

### 分析平台层

| 项目 | 定位 | 支持链 | 部署成本 | 适合阶段 |
| --- | --- | --- | --- | --- |
| **GraphSense** | 开源链上分析平台（奥地利 AIT 出品） | BTC / BCH / LTC / ZEC / ETH 等 | 高（需 Cassandra + 数据导入） | 中长期基础设施 |
| **Blockscout** | 开源区块浏览器 | EVM 系 | 中 | 需要私有浏览器时 |

**GraphSense 的判断**：这是目前唯一像样的开源分析平台，学术机构维护，方法学透明。但它的数据导入流程重、TRON 不在支持列表里（而 TRON 恰恰是我们最需要的）。**结论：作为方法学参考和 ETH/BTC 分析工具保留，不作为主力。**

### Blockscout 部署实测

2026-11 按官方 `docker-compose` 完整部署过一次，结论：**能跑通，但"部署成功"和"能拿到真实链数据"之间隔着一个 TB 级的选择。**

| 实测项 | 结果 | 对选型的影响 |
| --- | --- | --- |
| 镜像版本 | ghcr 上 `latest` 标签实际锁定 v9.0.2（构建于 2025-08），与仓库 master 源码不同步 | 新版本才有的环境变量在旧镜像上**静默失效**，不报错，只表现为连接失败，排查成本高 |
| 数据库连接 | 旧镜像读 `ECTO_USE_SSL`（默认 true），而 compose 内置的 postgres 未开 SSL | 必须显式设 `ECTO_USE_SSL=false`，否则后端在 "ssl not available" 上无限重启 |
| 可选组件 | `nft_media_handler` 要求配置 `NFT_MEDIA_HANDLER_NODES_MAP` 且能通过 Erlang 分布式协议连上后端 | 未配置时容器崩溃循环；无 NFT 业务时应直接不启用 |
| 索引范围 | 一次部署只服务一条链，由 RPC 地址决定 | 多链 = 多套部署，不存在"一套通吃" |
| 全量索引成本 | 以太坊主网全量索引为 TB 级存储、以天计的同步时间 | 与"按需查询"差一个数量级 |

**两种接入模式必须分清**，这是选型的关键：

| 模式 | 是否要落地全链数据 | 适用场景 | 成本 |
| --- | --- | --- | --- |
| **全量索引**（Blockscout 的工作方式） | 要，逐块搬运进本地库 | 做通用浏览器、实时监控大批地址 | TB 级存储 + 独立节点 |
| **按需查询**（调它的 API 或第三方 API） | 不要，查到哪算哪 | 具体案件、定向分析 | 几乎为零 |

::: tip 实测佐证
用公开实例的 REST API 按需拉取单个涉案地址的完整转出记录（含内部交易与 Token 转账），秒级返回，全程不需要本地索引。以公开案例 Ronin 跨链桥被盗案（`0x098b716b8aaf21512996dc57eb0615e2383e2f96`）为样本验证过：主地址转出的 7 笔万级 ETH 交易、后续地址向 Tornado Cash 分笔存入的记录，均可直接取到。**这说明定向分析完全不需要自建全量索引。**
:::

**如果决定 fork 自维护**（不再跟随上游），需要接受三件事，否则不建议走这条路：

1. **上游修复拿不到**。索引器的重组处理、合约解析这类底层 bug 修得频繁，fork 后要自己跟。
2. **Elixir 是硬门槛**。后端 Elixir/Phoenix，与团队现有 Python/Java 栈不同源，改索引逻辑的调试成本远高于旁挂服务。
3. **分析能力仍要另外写**。追踪、聚类、图谱不在它的职责范围内，改了源码这两块还是得自己实现——**改源码不会减少分析层的工作量**。

反过来说，fork 成立的唯一前提是：**必须改索引逻辑**（例如某类案件的合约结构它默认解析不了），且团队愿意长期承担 Elixir 维护。其余需求一律用旁挂方式解决。

### 可视化层

| 项目 | 适合 | 性能边界 |
| --- | --- | --- |
| Cytoscape.js | 交互式资金图，千级节点 | 万级需聚合 |
| AntV G6 | 快速原型，中文文档友好 | 同上 |
| Graphviz | 确定性静态图，用于报告 | 不支持交互 |

### 模型层

| 方向 | 代表工作 | 现实判断 |
| --- | --- | --- |
| 图神经网络地址分类 | Elliptic 数据集相关论文（GCN / GraphSAGE 类） | **可作为方法参考，不能直接落地**——训练数据是 2011–2013 年比特币数据，与当前 TRON/USDT 场景差异巨大 |
| 传统机器学习 | XGBoost / 随机森林 + 人工特征 | 需要标注数据，前期没有 |
| 规则引擎 | 自己写 | **第一阶段的唯一正确选择** |

## 三、推荐组合（去重后）

只推三件，其余一律不引入。

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 数据 | **公开 API（Tronscan + Etherscan 系）+ 本地缓存到 PostgreSQL** | 零门槛起步，缓存层让后续换数据源不影响上层 |
| 图计算 | **NetworkX** | 纯 Python，团队上手零成本，算法齐全；规模上去了再换 Neo4j |
| 可视化 | **Cytoscape.js** | 专用图库，布局与交互够用，能和前端原型直接对接 |

**明确不引入**：

- GraphSense（部署成本过高，且不支持 TRON）
- Neo4j（MVP 阶段节点数不够大，PostgreSQL + NetworkX 够用）
- 任何 GNN 框架（没有标注数据）
- 自建全节点（成本与收益不匹配）

::: tip 这套组合的边界
能支撑万级地址、十万级交易的分析。超过这个量级，图计算要换 Neo4j 或 ClickHouse。**到那时再换，现在不为未来买单。**
:::

## 四、明确不做的方向

| 不做 | 原因 |
| --- | --- |
| 自建全节点同步 | 存储与带宽成本高，公开 API 能满足定向分析需求；只有做通用浏览器或大规模实时监控时才需要 |
| 训练自己的地址分类模型 | 无标注数据；等有了一批人工核过的样本再说 |
| 做通用链上浏览器 | Blockscout 已实现且实测可用（见「Blockscout 部署实测」），自建全量索引是 TB 级投入，属重复造轮子 |
| 为"能用上开源分析平台"而改造它 | 追踪、聚类、图谱不在这类平台的职责范围内，改造不减少分析层工作量，只增加维护负担 |
| 支持全链 | 先做 TRON + ETH，其他链等有明确需求再扩 |
