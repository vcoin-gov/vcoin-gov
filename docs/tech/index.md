## 这一组解决什么

前两组回答"是什么"和"为什么难"，本组回答"**怎么做出来**"。产出不是调研报告，是能跑的东西——哪怕只是一个能自动跑完一轮筛查的脚本。

## 三篇专题的关系

| 顺序 | 专题 | 产出 | 判断标准 |
| --- | --- | --- | --- |
| ① | [开源项目调研](./oss-projects) | 候选池 + 评估 + **推荐组合（不超过 3 个）** | 能说清"为什么选它、为什么不选别的" |
| ② | [检测模型与原型](./detection-model) | 检测架构、评分体系、分阶段原型 | 能跑、能测、误报率可量化 |
| 补充 | [Blockscout 专题](./blockscout) | 单个开源项目的原理拆解、实测记录、二次开发路线 | 能回答"能不能改、改哪里、代价多大" |

主线是 ①②。第三篇是对重点候选的深挖——**只有真正部署过、评估过改造成本的结论，才敢写进选型表。**

::: tip 顺序不能反
先定工具再写代码。跳过调研直接动手，最后大概率发现数据拿不到、标签不可靠，返工成本远高于调研成本。
:::

## 本组的三条原则

1. **能跑优先于先进。** 先用规则跑通全流程，再考虑模型。没有标注数据就上深度学习，属于自娱自乐。
2. **可解释优先于准确。** 检测结果必须能说清"因为什么被判可疑"，否则在实战中没人敢用。
3. **去重优先于堆砌。** 同一个能力只留一个实现。装了三个功能重叠的工具，等于维护三份负担。

## 交付要求

| 项 | 要求 |
| --- | --- |
| 代码 | 放仓库 `code/` 目录，有 README 和运行说明 |
| 数据 | 不提交原始案件数据；测试用公开数据集或合成数据 |
| 文档 | 每个原型必须写清输入输出、运行环境、已知缺陷 |
| 评估 | 必须给出误报率/漏报率的测算方法，不能只说"效果不错" |
