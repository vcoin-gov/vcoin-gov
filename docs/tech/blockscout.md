## 结论摘要

1. **它是"数据落地 + 查询"工具，不是分析工具。** 追踪、聚类、资金图谱都不在其职责范围内，二次开发也改变不了这一点。
2. **全量索引与按需查询是两条完全不同的路。** 定向案件分析走后者，成本差一个数量级；前者只在"做通用浏览器"或"大规模实时监控"时才成立。
3. **二次开发有三条路：旁挂、fork、重写。** 优先旁挂；fork 成立的唯一前提是**必须改索引逻辑**，且团队愿意长期承担 Elixir 维护。
4. **真正值得借鉴的是它的分层设计**：索引与查询分离、标签多对多建模、抓取进度可续跑。

## 一、它怎么工作

### 1.1 组件构成

| 组件 | 技术栈 | 职责 |
| --- | --- | --- |
| 后端应用 | Elixir / OTP（多 app：`explorer`、`indexer`、`block_scout_web`、`ethereum_jsonrpc`） | 数据模型、抓取、API |
| 存储 | PostgreSQL | 全部链上数据的落地层 |
| 前端 | Next.js（独立仓库） | 页面渲染，只读 API |
| 数据源 | 外部 RPC 节点 | 区块、交易、收据、日志、trace |

一个部署实例只服务**一条链**，由 `ETHEREUM_JSONRPC_HTTP_URL` 决定接谁。多链 = 多套部署。

### 1.2 索引流水线

```
连接 RPC → 读链 ID 与最新块高
   ↓
从指定块开始，逐块拉取 block + receipts + logs
   ↓
解析：普通交易 / 内部交易（需 trace）/ Token 转账（解析日志）/ 余额变化
   ↓
写入 PostgreSQL，同时更新 last_fetched_counters 记录抓取进度
   ↓
API 只读查询，前端只调 API
```

两个关键点：

- **内部交易不是独立交易**，要额外开 trace 才能拿到，单独存一张表。这是"主交易列表看不到大额转账"的根因。
- **抓取进度单独记表**（`last_fetched_counters`），进程重启后从断点续跑，不用从头再来。

### 1.3 数据落在哪些表

| 表 | 存什么 | 追踪分析时怎么用 |
| --- | --- | --- |
| `blocks` | 区块头 | 定位时间窗、确认区块高度 |
| `transactions` | 普通交易（EOA 发起） | 资金流向的主干 |
| `internal_transactions` | 合约内部转账 | **大额资金常在这里，容易漏** |
| `token_transfers` | ERC-20/721 转账 | USDT 等稳定币的实际流向 |
| `tokens` | 代币元数据（精度、符号） | 换算金额时必须用 decimals |
| `addresses` | 地址、余额、合约标记 | 地址画像 |
| `address_current_token_balances` | 当前 Token 持仓 | 判断"钱还在不在" |
| `address_tags` / `address_to_tags` | 标签与多对多关联 | **自建标签库的落点** |
| `smart_contracts` | 已验证源码、ABI | 判断合约性质（混币器、桥） |
| `logs` | 事件日志 | 解析非标准合约行为 |

### 1.4 查询层

对外是 REST API v2（`/api/v2/addresses/{hash}/transactions`、`/token-transfers` 等），只读。

但更快的用法是**直连它的 PostgreSQL**——`SELECT` + `JOIN` + 聚合，比翻页调 API 快一到两个数量级。前提是只读权限，别写它的表。

## 二、我们的验证记录

### 2.1 部署链路

官方 `docker-compose` 的实际启动顺序：`db-init`（改数据目录权限）→ `db`（等 init 完成）→ `backend`（先跑 migration，再启动服务）。后端启动时会校验数据库连接，连不上就退出，靠 `restart: always` 无限重试——所以故障表现是"无限重启"而不是"报错退出"。

### 2.2 踩到的四个坑

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| backend 无限重启，日志刷 `ssl not available` | 镜像 `latest` 实为 v9.0.2（2025-08 构建），读的是旧变量 `ECTO_USE_SSL`（默认 true）；而 compose 内置 postgres 未开 SSL | 显式设 `ECTO_USE_SSL=false`，与新版 `ECTO_SSL_MODE=disable` 并存 |
| 按文档配的新环境变量完全不起作用 | 镜像版本落后于仓库源码，新变量在旧版本里不存在，**静默忽略不报错** | 固定镜像 tag 与源码版本对齐，或改为从源码构建 |
| `nft_media_handler` 崩溃循环，报 `NODES_MAP must contain at least one node` | 该组件是远程派发 worker，需要 `NFT_MEDIA_HANDLER_NODES_MAP` 且能连上后端 Erlang 节点；compose 里 `RELEASE_NODE` 还硬编码了容器 IP | 无 NFT 业务时直接不启用（`profiles` 排除） |
| 页面 502，但 API 正常 | nginx 启动时只解析一次 Docker DNS，后端/前端容器重建后 IP 变化，upstream 仍指向旧 IP | 重启 proxy 临时恢复；根治用 `resolver 127.0.0.11 valid=10s` + 变量式 `proxy_pass` |

::: warning 通用教训
**"部署成功"不等于"配置生效"。** 容器起来了、健康检查过了，不代表你设的环境变量被读取了——版本不一致时，未知变量会被安静丢弃。排查这类问题的顺序应该是：先确认镜像实际版本，再确认变量是否在该版本存在，最后才看业务日志。
:::

### 2.3 成本实测

| 模式 | 是否要落地全链数据 | 存储 | 首次可用时间 | 适用场景 |
| --- | --- | --- | --- | --- |
| 全量索引 | 要，逐块搬运进本地库 | TB 级（以太坊主网） | 以天计 | 通用浏览器、大规模实时监控 |
| 按需查询 | 不要，查到哪算哪 | MB~GB 级 | 分钟级 | 具体案件、定向分析 |

用公开案例（Ronin 跨链桥被盗案，主地址 `0x098b716b8aaf21512996dc57eb0615e2383e2f96`）验证过：单地址的完整转出记录、内部交易、后续向混币器的分笔存入，全部可通过 API 按需取到，**全程不需要本地索引**。

## 三、能力边界

| 需要的分析能力 | Blockscout 是否提供 |
| --- | --- |
| 存链上数据、按地址查交易 | 提供 |
| 内部交易、Token 转账明细 | 提供 |
| 多跳资金追踪 | 无 |
| 地址聚类（判断同一控制人） | 无 |
| 资金流向图 | 无 |
| 案件管理、证据包导出 | 无 |
| 非 EVM 链（TRON / BTC） | 无 |

::: danger 选型前提
TRON 是国内涉 USDT 案件的主力链，Blockscout **完全不支持**。这意味着它在完整方案里最多覆盖三分之一场景，不能当作底座。非 EVM 的数据源必须另行解决。
:::

## 四、二次开发路线

### 4.1 三条路对比

| 路线 | 改动量 | 能拿到什么 | 主要代价 |
| --- | --- | --- | --- |
| **旁挂**（不动源码） | 小 | 完整原始数据 + 完全自主的分析层 | 需要自己写全部分析能力 |
| **fork 改造** | 大 | 可改索引逻辑、可加自有表与接口 | Elixir 门槛 + 上游修复拿不到 |
| **重写** | 最大 | 架构完全自主 | 索引器的坑要重新踩一遍 |

### 4.2 路线 A · 旁挂（推荐）

```
Blockscout（只读数据源）
   ├─ 直连 PostgreSQL 只读（分析查询走这里）
   └─ REST API v2（明细核验走这里）
        ↓
自己的分析服务（Python/FastAPI + Neo4j + 前端）
```

优点：不碰源码，能持续跟随上游升级；分析逻辑用 Python 写，团队上手零成本；直连数据库后查询性能远好于翻页调 API。

边界：改不了索引行为——如果某类合约的转账它解析不出来，旁挂也拿不到。

### 4.3 路线 B · fork 改造

真要改，值得动的只有三处：

| 改动位置 | 目的 | 难度 |
| --- | --- | --- |
| `apps/indexer/` 下的 fetcher 模块 | 增加对特殊合约/事件的解析 | 高，需要理解 OTP 进程模型 |
| `apps/block_scout_web/` 的 API controller | 增加定制接口 | 中，Phoenix 有固定套路 |
| `priv/repo/migrations` + 自定义表 | 存自己的业务数据 | 低，但要在自己的库做更省事 |
| 前端（独立仓库） | 加页面 | 中，但要跟着上游前端一起升级 |

必须接受的三个代价：

1. **上游修复拿不到**。重组处理、合约解析这类底层 bug 修得频繁，fork 之后要自己跟。
2. **Elixir 是硬门槛**。与团队现有的 Python/Java 栈不同源，调试成本远高于旁挂服务。
3. **分析层工作量不减**。改了源码，追踪/聚类/图谱照样要从零写。

### 4.4 路线 C · 重写

只有在两个条件同时成立时才考虑：既要支持非 EVM 链、又需要深度定制索引逻辑，此时 Blockscout 的架构会成为负担。

重写的正确姿势不是"照着抄"，而是**只借鉴它的数据模型**（表结构、标签模型、抓取进度表），索引器用自己的技术栈实现。

## 五、可借鉴的四个设计

| 设计 | 做法 | 我们能用在哪 |
| --- | --- | --- |
| 索引与查询分离 | 抓取进程只写库，API 只读库 | 分析服务与抓取服务解耦，互不影响 |
| 标签多对多 | `address_tags` + `address_to_tags` | 一个地址可挂多个标签（交易所 + 涉案 + 高风险），比单字段灵活 |
| fetcher 按数据类型拆分 | 区块 / 内部交易 / Token 转账 / 余额各一个独立进程 | 某一类抓取失败不阻塞其他类型 |
| 抓取进度落表 | `last_fetched_counters` 记录每类数据的进度 | 断点续跑，重启不用从头再来 |

## 六、局限与待验证

- 【待验证】不同版本间的环境变量差异未做系统性比对，本文坑点仅覆盖 v9.0.2 与当前 master 的差异。
- 【待验证】索引器在真实主网规模下的性能未压测，TB 级成本来自公开资料与经验估算。
- 【推断】多实例/集群模式下的一致性表现未验证（编译配置中存在 `APPLICATION_MODE` 分离部署能力，但未实测）。
- 未覆盖非 EVM 链路，TRON 的等价方案需要单独调研。
