## 本页要回答的问题

1. **资金树**和**资金流转图**有什么本质区别？什么时候用哪个？
2. 上万个节点怎么画才不糊成一团？聚合、折叠、时间切片各适合什么场景？
3. 布局算法怎么选？力导向好看但不可读，分层布局可读但会丢信息——怎么权衡？
4. 一张图要能当**证据**用，需要满足什么条件？（这是和"好看的图"的根本区别）
5. 原型用什么技术栈？自建还是接现成可视化库？

::: tip 先定一个判断标准
可视化的目的不是让图好看，是让**结论可验证**。任何一张图，如果读者无法从图上复算出一个数字，这张图就只能当封面，不能当证据。
:::

## 一、两种图，别混用

这是本页最重要的一节。实务中最常见的问题是把两种图混着做，结果两边都不达标。

| 维度 | 资金树（Fund Tree） | 资金流转图（Flow Graph） |
| --- | --- | --- |
| 结构 | **树**，无环，一个根 | **有向图**，允许环路与汇聚 |
| 起点 | 固定（被害人地址 / 案件地址） | 任意或全体 |
| 展开方式 | 按跳数（1 跳、2 跳、3 跳） | 按资金关联自然形成 |
| 回答的问题 | 这笔钱去了哪、经过几层 | 这帮人怎么组织的、谁在中间 |
| 主要用途 | **举证、汇报、还原单案** | **发现团伙结构、找归集点** |
| 缺点 | 合并账户画不出（同一地址多次出现） | 节点爆炸，可读性差 |
| 典型规模 | 几十到几百节点 | 几千到几万节点 |

**一句话区分**：资金树是**追一笔钱**，资金流转图是**看一伙人**。

::: warning 资金树的常见错误
把同一地址在不同跳数重复画出来，看起来是树，实际是图——这会让读者误以为有多条独立资金流。正确做法是**同一地址只出现一次，用连线表示多跳关系**，或者在节点上标注"第 N 跳再次出现"。
:::

## 二、规模问题：万级节点怎么画

节点一多就糊，这是绕不过去的。四种处理方式，各有代价：

| 方法 | 做法 | 适合场景 | 代价 |
| --- | --- | --- | --- |
| 阈值裁剪 | 只画金额 ≥ X 的边 | 快速定位主干路径 | 小额拆分结构被隐藏（而小额拆分本身就是特征） |
| 地址聚合 | 把聚类后的一簇画成一个节点 | 团伙结构展示 | 丢失簇内细节，聚合本身有误差 |
| 分层折叠 | 按 L1–L5 层聚合，逐层展开 | 讲清结构 | 交互复杂，不适合静态截图 |
| 时间切片 | 按时段分别成图 | 展示资金推进过程 | 跨时段的关联看不到 |

**建议组合**：**先聚合再展开**。默认视图按聚类折叠成一簇一簇，点开某簇才展开内部地址。这样首屏能看懂结构，细节按需下钻。

::: tip 单案不需要聚合
项目0 只有 312 行流水，去重后 142 笔，聚合出 **46 个节点、55 条边**——这个量级直接全量画就行，聚合并不会让它更好读。上面四种手段是给万级节点准备的，别在小案子上过度设计。
:::

## 三、布局怎么选

| 布局 | 效果 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 力导向（force-directed） | 节点互相排斥、边像弹簧 | 自然、能看出社团 | 每次渲染结果不同，**不能当证据** |
| 分层（dagre / 层级） | 从上到下按跳数排列 | 可读、可复现、像资金树 | 环路处理难看 |
| 环形 / 径向 | 以根为中心向外扩散 | 适合星形结构的资金盘 | 深链路会重叠 |
| 地理/时间轴 | 按时间排布 | 展示节奏 | 空间关系丢失 |

**结论**：**举证用分层布局，探索用力导向**。同一个数据集可以出两张图，用途不同。凡是进报告、进证据的图，必须用确定性布局（同样的数据，任何人生成出来都一样）。

这不是一句口号，我们用同一份数据实测过（同一台机器、Chrome、两个画布各 550×755）：

| 检验 | 做法 | 结果 |
| --- | --- | --- |
| 预设坐标是否确定性 | 同一份 `data.json` 重建两次，对整块画布取 SHA-256 | Cytoscape ✓ 两次同像素；G6 ✓ 两次同像素 |
| 力导向是否可复现 | 自写 260 次迭代的弹簧模型，随机初值，连跑两遍 | 46 个节点 **100% 移动**，每次结果都不同 |
| 环路怎么摆 | 回流边（吴刚→张海涛）从右侧绕行，不与主干交叉 | 可读，但需要手工给坐标 |

所以 demo 里"力导向"只作为探索视图存在，并明确标注"每次结果不同"；一切能进证据的视图都走**预设坐标**。

## 四、技术选型

| 方案 | 定位 | 适合 | 不适合 |
| --- | --- | --- | --- |
| **Cytoscape.js** | 专用图可视化库 | 千级节点、需要丰富布局与交互 | 需要炫酷动效的展示 |
| **AntV G6** | 图可视化引擎，中文文档 | 快速搭原型、需要开箱即用交互 | 超大规模性能瓶颈 |
| **ECharts graph** | 通用图表库的图类型 | 简单关系图、和已有 ECharts 项目集成 | 复杂交互 |
| **D3.js** | 底层可视化库 | 完全自定义 | 开发成本高，不划算 |
| **Graphviz** | 命令行布局 | 生成静态证据图（确定性布局） | 交互 |
| **Neo4j Bloom / 浏览器** | 图数据库自带可视化 | 已有 Neo4j 时顺手用 | 许可与部署成本 |

**推荐路线**：数据侧用 **NetworkX** 做图计算（最短路、社区发现、中心度），渲染侧用 **Cytoscape.js** 或 **G6** 做交互原型，出报告时用 **Graphviz 生成确定性布局的静态图**。

这样分工的好处：计算和渲染解耦，换渲染层不影响分析逻辑。

### Cytoscape.js vs G6：同一份数据实测

两个引擎吃**同一个 `data.json`**（同一份节点、边、金额、预设坐标），并排渲染：

| 指标 | Cytoscape.js 3.35 | AntV G6 5.1 |
| --- | --- | --- |
| 首帧渲染（46 节点 / 55 边，含数据加载与渲染器初始化） | ≈ 148–166 ms | ≈ 1.25–1.51 s（含渲染器初始化） |
| 同页重建（数据已在内存） | ≈ 16–21 ms | ≈ 1.50 s |
| 固定坐标 | 原生 `position` + `preset` 布局 | 节点 `style.x/y`，且**不传 layout**（v5 实测保留） |
| 同数据重建像素一致 | ✓ | ✓ |
| 交互 | 点选 / 缩放 / 拖拽内置 | 同，另有内置 behaviors |
| 打包体积（min.js） | 442 KB | 1,383 KB（约 3.1 倍） |
| 中文文档 | 一般 | 好 |

**结论**：单案、千级节点、有"图要能复算"的要求，用 **Cytoscape.js** 更省事；要快速出交互原型、团队熟悉 AntV 生态，用 **G6**。两者都能吃同一份快照，切换成本很低——真正的成本在数据口径，不在渲染库。

::: warning 这个耗时不等于性能结论
上表是单机单次首帧测量：样本只有 46 个节点，**不能**用来判断万级图谁更快。G6 的耗时主要在渲染器初始化，且**后台标签页会被浏览器节流**（实测同样代码在后台标签页跑到 3.5 s 以上），比较时务必把窗口切到前台。要比性能得另做压测。
:::

## 五、让图能当证据的四条要求

| 要求 | 具体做法 |
| --- | --- |
| **可复现** | 数据快照固定（写明区块高度或抓取时间），布局确定性，任何人重跑得到同一张图 |
| **可溯源** | 每条边都能点开看交易哈希，图上标注金额单位与精度 |
| **可复算** | 图上要有汇总数字（总流入、总流出、跳数），读者能对得上 |
| **标注清楚** | 地址标签注明来源与时间；推断的边用虚线；聚类节点注明置信度 |

**反例**：一张漂亮的力导向图，没有时间戳、没有交易哈希、节点不标金额——这在法庭上没有意义。

本次原型的落地方式：

1. **可复现**：`data.json` 自带 `sha256`，覆盖全部节点与边的关键字段；`verify_snapshot.py` 只用冻结的 `txns.csv` 重跑一遍，14 项全部 PASS 才算通过。
2. **可溯源**：每条边带 `evidence: [txn_id, ...]`，点开节点/边能看到证据流水号，可回 `demo.db` 逐笔核对。
3. **可复算**：节点详情里的"复算"把当前图中该节点的入/出边金额相加，与快照记录比对，两边一致才打 ✓。
4. **标注清楚**：金额统一两位小数、单位元；`certainty: observed` 表示来自真实流水，推断边用虚线（本案例全部为 observed，暂无推断边）。

## 六、团伙资金分层模式怎么画

这是可视化里最有价值的一类图。不要画全量图，画**结构图**：

```
被害人池 ──▶ L1 收款地址（一次性，大量）
                  │
                  ▼
            L2 拆分地址（扇出，数量激增）──▶ 部分回流
                  │
                  ▼
            L3 归集地址（扇入，数量收敛）◀── 关键节点
                  │
                  ▼
            L4 清洗（混币 / 跨链 / 交易所）
                  │
                  ▼
            L5 变现（OTC / 境外）
```

画的时候要突出三件事：

1. **收敛点在哪**（L3）——这是打击着力点
2. **扇出宽度**（L2）——反映组织规模
3. **时间跨度**——从 L1 到 L5 用了多久，反映专业程度

### 项目0 实例（银行卡流水，非链上）

[![项目0 涉诈资金五层结构示意图](/img/onchain/five-layers.svg)](/img/onchain/five-layers.svg)

*图：项目0 五层资金结构（点击看大图；金额单位：元；箭头上的数字为层间聚合金额，虚线为回流路径；节点上「入 / 出」为该账户在全案中的累计值）*

::: warning 为什么用银行卡流水讲链上结构
示例数据来自 `economic_detect` 的 demo 库（银行 + 微信 + 发票），不是链上交易。选它是因为**结构同构**：链上把"卡号"换成"地址"，分层、收敛、扇出、回流、沉淀的判断逻辑完全一样，差异只在 L5——链上是交易所提现/OTC，银行卡是 ATM 取现和商户消费。凡涉及金额的地方都以真实流水复算为准，不做类推。
:::

| 层 | 职责 | 本项目对应 | 金额（元） |
| --- | --- | --- | --- |
| L0 | 被害人池 | 32 个账户 | 合计转出 426,804.00 |
| L1 | 收款池（收敛） | 张海涛 6227…0001 | 入 454,051.27 / 出 454,051.27 |
| L2 | 二级卡（扇出） | 李国栋 / 王丽娟 / 赵鹏 | 240,649.27 / 128,041.20 / 85,360.80 |
| L3 | 水房归集 | 孙志强 6227…0005 | 入 = 出 405,463.80 |
| L4 | 取现 / 沉淀 / 回流 | 周敏 / 郑小云 / 吴刚 | 入 219,911.01 / 162,185.52 / 35,247.27 |
| L5 | 外部对手 | ATM 取现 + 3 家商户 | 192,627.92 / 21,340.20 |

三个判读点的具体数字：

- **收敛点**：32 个被害人账户 → 1 张一级卡，一级卡侧共 33 笔入账（32 个对手 + 1 笔回流），入金 454,051.27。入向 33、出向仅 3，**"分散转入、集中转出"** 的形态在图上是一眼可见的漏斗。
- **扇出宽度**：一级卡只向 3 张二级卡转出（240,649.27 / 128,041.20 / 85,360.80，合计 454,051.27），扇出比 1:3——比"1 拖 50"的小型水房收敛，说明这是**有分工的团伙**而不是散兵。
- **时间跨度**：图中首笔 2024-03-01 02:10:05，末笔 2024-03-08 15:20:00，约 **7 天 13 小时**走完 L0→L5。夜间（00:00–06:00）集中入账是被害人侧的特征，与"白天上班、晚上被骗"的报案描述吻合。

另外三处只能在图上看到、报表里看不到的结构：

| 现象 | 图上表现 | 判读 |
| --- | --- | --- |
| 沉淀 | 郑小云 162,185.52 只进不出 | 钱停在账上不动，是"等风声"还是"待分配"，需要结合后续流水 |
| 回流闭环 | 吴刚 → 张海涛 27,247.27，走右侧绕行边 | 张→李→孙→吴→张 构成闭环，是认定"同一团伙"而非"多层转手"的关键 |
| 对倒 | 周敏 ↔ 吴刚 6,000 / 5,880，各 3 笔 | 小额往返常见于试探账户是否被冻结，也可能是分赃结算 |

还有一个**不能想当然**的地方：李国栋账上留存 27,247.27 未归集，而吴刚回流到张海涛的金额也恰好是 27,247.27。两者数值相同，但路径不同（后者来自孙→吴 29,247.27 这条线），**不能据此认定是同一笔钱**——金额对齐只是核查线索，不是结论。

## 八、数据模型（已定稿）

P0/P1 用的快照格式，两个引擎共用。字段不多，但**必填项就是验收项**——少一个就无法复算。

**节点**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | ✓ | 账户号；虚拟节点用可识别前缀（如 `ATM-CASH-001`） |
| `name` | string | ✓ | 展示名；被害人脱敏为「受害人01」 |
| `kind` | enum | ✓ | `person` / `merchant` / `atm` / `wechat` |
| `layer` | 0–5 | ✓ | 层级，决定颜色与纵向位置 |
| `role` | string | ✓ | 收款池 / 二级卡 / 水房 / 取现 / 沉淀 / 回流 / 外部对手 |
| `in` / `out` | number | ✓ | 聚合入金 / 出金，两位小数 |
| `txnCount` | int | ✓ | 关联流水行数 |
| `x` / `y` | number | ✓ | 预设坐标，证据图必须写死 |
| `note` | string | | 判读备注 |

**边**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | ✓ | `E000` 顺序编号 |
| `source` / `target` | string | ✓ | 节点 `id` |
| `amount` | number | ✓ | 聚合金额（两位小数） |
| `count` | int | ✓ | 聚合笔数 |
| `firstTs` / `lastTs` | string | ✓ | 首笔 / 末笔时间（`YYYY-MM-DD HH:MM:SS`） |
| `evidence` | int[] | ✓ | `txn_id` 列表，可回库逐笔核对 |
| `certainty` | enum | ✓ | `observed`（实测边）/ `inferred`（推断边，画虚线） |

**三条去重口径**（不定这三条，金额一定对不上）：

1. **只从出账行建边**。入账行用来核对镜像（本案 167 条入账里 132 条能匹配到出账行）。如果入账行也翻成边，镜像会被算两次——我们试过，张海涛出金会被算成 912,855.27，正确值是 454,051.27。
2. **同一 `(出方, 入方, 金额, 时间)` 视为重复**。本案银行侧存在整行重复（受害人01 有 4 条相同的 19,999），去重剔除 59,997.00。
3. **找不到对应出账行的入账不入图**。本案 35 条、合计 518,804.00，其中 32 条是受害人账上的"工资入账"、3 条是微信双侧时间戳差 30 秒导致匹配失败。这些只记在 `meta.counts.orphanInRows` 里，画上去会把被害人的正常收入当成诈骗资金。

## 九、复现步骤

仓库里已带冻结数据，**不需要数据库也能复算**：

```bash
# 1) 生成快照（读 demo.db，输出 data.json，并可冻结原始行为 CSV）
python prototypes/fund-graph/build_snapshot.py \
  --db examples/demo.db \
  --out docs/public/demo/fund-graph/data.json \
  --freeze prototypes/fund-graph/txns.csv

# 2) 复算校验：只用冻结的 txns.csv 重跑同一套口径，14 项全 PASS 才算过
python prototypes/fund-graph/verify_snapshot.py

# 3) 生成五层示意图（数字先断言再画，数据变了会直接报错）
python prototypes/fund-graph/make_layers_svg.py

# 4) 本地预览
npm install && npm run dev
```

判定标准只有一条：`verify_snapshot.py` 输出 `RESULT: PASS`、退出码 0。当前快照 `sha256 = f0b632f6fbb74b830e8b40850d28f6b5cca501b3ce263ec8a5bf72a0fe3b8ce4`，任何人重跑都应得到这个值；对不上说明数据或口径被改过。
